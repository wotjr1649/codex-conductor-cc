## Outcome

Make the fork correct and fast on its primary runtime, keep POSIX support alive, and build the
machinery that lets a fully independent fork absorb upstream work by hand without drifting blind.

## Decisions

Decided by the maintainer on 2026-08-14. Inputs, not proposals.

1. **Hard fork.** Nothing is contributed back. Upstream changes are analyzed individually and
   absorbed or rejected, never merged wholesale.
2. **Direct implementation.** Every finding is fixed here. Upstream pull requests covering the
   same ground are reference material, not a delivery channel. Rebase friction is not an ordering
   constraint.
3. **Windows x64 first, POSIX preserved.** Daily use is Windows. Linux and macOS stay correct so a
   later move does not require rediscovery, but Windows pain sets the order.

## Measured evidence

Measured twice by independent harnesses. The second measurement landed 10–14 percent higher than
the first; the numbers below are the second, conservative-side set. Reproduce before and after the
performance phase.

Per-call cost of the state-path resolution chain:

| Call | ms/call |
| --- | --- |
| `resolveCommandInvocation("git")` — executable lookup only | 38.7 |
| `runCommand("git", ["rev-parse", "--show-toplevel"])` | 68.5 |
| `resolveWorkspaceRoot()` | 69.7 |
| `resolveStateDir()` | 69.1 |

Causal attribution is settled, not inferred. Bare `spawnSync` of the two executables sums to
69.12 ms against a measured `resolveStateDir` of 69.11 ms; all non-spawn work in that function —
`realpathSync.native`, sha256, path joins — totals **0.04 ms**, or 0.06 percent. It is process
creation, not filesystem work, not hashing, not module load.

Three processes are created per call, not two: `where.exe` resolves `git` to a 46 KB
Git-for-Windows launcher which then spawns the real 4.4 MB binary. The launcher costs 8.4 ms of
the 69.

Amplification by record count:

| jobs | `loadState()` | `upsertJob()` |
| --- | --- | --- |
| 0 | 68.6 ms | 277.8 ms |
| 1 | 138.2 ms | 481.7 ms |
| 10 | 779.2 ms | 2,395 ms |
| 50 (`MAX_JOBS`) | 3,557 ms | 10,774 ms |

**The amplifier is record shape, not record count.** `assertManagedLogFile` returns at
`state.mjs:96` when `logFile` is null, before reaching `resolveJobsDir`. With 50 records that
carry no `logFile`, `loadState` costs 70.2 ms and makes one resolution instead of 51. Tracked jobs
do set `logFile` (`tracked-jobs.mjs:149,192`), so the expensive shape is the normal one, but the
scaling claim must be stated against shape.

Instrumented resolution counts: `loadState` = n+1, `upsertJob` = 3n+4. A linear model at 69.1 ms
predicts within 1.2 percent of measurement.

**Generalizability.** Decomposing the 38.7 ms lookup by PATH length gives roughly 16 ms process
creation floor, 13 ms enumerating real system directories (unavoidable on any Windows host), and
9 ms from this machine's 173-entry PATH. Only that last 23 percent is machine-specific. Node
overhead is excluded — .NET `Process.Start` measures 37.9 ms on the same binary. Antivirus
first-scan is excluded — a renamed copy cost 40.6 ms cold and 17.2 ms warm, and the medians
measure the warm path. The shape generalizes; the exact number does not.

**Measured effect of the fix**, not estimated:

| Variant | per call | `loadState` n=50 | `upsertJob` n=50 |
| --- | --- | --- | --- |
| today | 69.1 ms | 3,524 ms | 10,641 ms |
| executable lookup cached | 29.2 ms | 1,489 ms | 4,497 ms |
| + bypass the launcher | 21.3 ms | 1,086 ms | 3,280 ms |
| workspace root memoized per cwd | 0.05 ms | **71.6 ms** | **76.8 ms** |

**Observed production state.** The maintainer's five real workspaces hold 0, 1, 0, 1, 0 jobs, so
today's per-turn hook cost is roughly 345 ms, not the multi-second worst case. One workspace holds
0 indexed jobs against 8 artifact files on disk, confirming the retained-artifact finding in
production. Two of five hold a stale `broker.json`, which is the precondition for the POSIX wedge
below. The correct framing is that this degrades linearly toward the worst case with use, not that
it is catastrophic today.

## Platform reachability

On Windows the broker listens on a named pipe and sets `authenticated` true at connection
(`app-server-broker.mjs:168`), so no exported function of `lib/broker-auth.mjs`,
`lib/worker-control.mjs`, or `lib/runtime-paths.mjs` is reached in production on win32 — 644 lines,
9.1 percent of the runtime. Two qualifications:

- The module bodies still evaluate on every Windows process, because all three are static ESM
  imports. Regex compilation, Set construction, and transitive `node:crypto`/`node:net` loading are
  paid by every invocation including the already-over-budget `SessionEnd` hook.
- Four files under `tests/portability/` call into them with no win32 skip, so `broker-auth.mjs`'s
  crypto surface is in fact exercised on Windows by the suite. "Unverified on the primary runtime"
  would be wrong; "not reached in production on win32" is right.

## Finding catalog

### Availability

| ID | Location | Finding |
| --- | --- | --- |
| `C6` | `codex.mjs:302-337,606` | **The highest-value defect in this catalog.** `rejectCompletion` is assigned three times and **called nowhere**. `completeTurn` is the only settle path for a turn's completion promise, reached only by a `turn/completed` notification or the 250 ms inference timer. When the app-server dies mid-turn, `handleExit` rejects only *pending requests* — `turn/start` already returned, so there are none — and `await state.completion` never settles. Foreground against a directly spawned app-server: the job stays `running` forever and the CLI exits **code 0 with no output**. Foreground through the broker, which is the default path on every platform: the CLI never exits at all, because `C7` holds its socket open — measured at 60 s and still running, job left `running`. POSIX background: the worker's listening control socket keeps the loop alive, producing an unkillable process. Trigger needs no unusual input. This is the shared mechanism behind the upstream "stuck running forever" cluster. |
| `C7` | `app-server-broker.mjs:112,162` | Found while fixing `C6`, not by the original pass. Nothing subscribes to the broker's `appClient` exit, so the broker never observes its own app-server dying: it keeps listening, keeps every client socket open, and keeps accepting requests. Writes to the exited child are silently discarded — verified on Node 24.19.0 that `end()` and `write()` against an exited child's destroyed stdin neither throw nor emit — so every later request stays pending forever with no reply and no error. The broker becomes a permanent black hole for that workspace, and `ensureBrokerSession` reuses it because its endpoint still answers a readiness probe. This is the transport half of `C6`: with the broker in the path a client cannot even observe the connection loss that `C6` fails to act on. |
| `C1` | `broker-lifecycle.mjs:131,284-287,334,340-345` | POSIX only, fork-introduced. On POSIX the **only** route that deletes `broker.json` is a fully successful authenticated shutdown handshake: `clearBrokerSession` has two non-test call sites, one Windows-only (`:354`) and one reached only when `brokerStopped` is true (`session-lifecycle-hook.mjs:181`). Any other broker death — kill, crash, OOM, or a `SessionEnd` hook killed by `C3` — leaves the file, and every later invocation writes `phase: "indeterminate"` and throws. Diagnostics die with it: `getSessionRuntimeStatus` loads broker state unguarded (`codex.mjs:909`), so `/codex:setup` and status also throw and the plugin cannot report its own broken state. Blast radius is one workspace. Windows self-heals by returning `null`. |
| `C2` | `app-server-broker.mjs:31,118,206`, `broker-auth.mjs:136` | POSIX only. The broker's nonce set is added to and never pruned. At 4,096 entries all authentication fails. A readiness probe consumes a nonce, and a probe whose *client read* times out after the broker has already recorded the nonce consumes one while still reporting failure, so one `waitForBrokerEndpoint(session, 2000)` can burn about 40 under load. The practical floor is well under 2,048 operations, not 4,096. The process stays killable by signal — what is lost is the plugin's own shutdown route, and on POSIX `teardownBrokerSession` never kills a pid at all, so no in-plugin path stops a POSIX broker. |
| `C3` | `hooks/hooks.json:21`, `session-lifecycle-hook.mjs:56-182` | `SessionEnd` declares 5 s; upstream issue #582 records Codex clamping it to 3 s, verified against the issue body, and upstream #474 independently reports cleanup already exceeding 5 s. The hook is killed, `clearBrokerSession` never runs, and on POSIX this is what arms `C1`. |
| `C4` | `app-server-broker.mjs:266-269` | No timer of any kind exists in the file. Shutdown is refused while an authenticated connection is registered. **Windows is unaffected** — that set is never populated for pipe endpoints. On POSIX both `close` and `error` deregister, so pinning requires a file descriptor that outlives the client (inherited by a fork, or a hung-but-alive client), not merely a dead client. What holds on both platforms is that nothing reclaims an orphaned broker. |

### Correctness and security in argument handling

| ID | Location | Finding |
| --- | --- | --- |
| `A1` | `args.mjs:31-34` via `codex-companion.mjs:141-153` | **Crosses a permission boundary from prose.** Slash commands pass `"$ARGUMENTS"` as one shell argument, so the whole string is re-tokenized and every token is scanned as a possible option with no end-of-options rule. A read-only request whose text contains `--write` sets `options.write`, and `executeTaskRun` then passes `sandbox: "workspace-write"` (`codex-companion.mjs:508`). Codex gets repository write access against an explicit read-only instruction, with no warning, and the token is deleted from the prompt. `--model` in prose swallows the next word; `--background` silently detaches. |
| `A2` | `args.mjs:89-92` | `splitRawArgumentString` consumes backslashes unconditionally, before the quote check. On the declared primary platform this means `C:\Users\...` becomes `C:Users...`: `/codex:transfer --source` can never work with a native Windows path, and any prompt containing a backslash is silently corrupted before it reaches the model. Apostrophes are deleted too, and an odd count swallows the remainder into one quoted token. 100 percent reproducible. |
| `A3` | `args.mjs:28` | `token.slice(2).split("=", 2)` discards everything after a second `=`, so `--cwd=/a/b=2/c` resolves to `/a/b` and the command — including a write task — runs against the wrong directory with no error. |

## Ordering principle

1. Cheap, independent, high-severity fixes come first regardless of which subsystem they belong to.
2. Touch each file cluster once.
3. Respect dependencies: the hook-budget phase cannot succeed before the performance phase.
4. Split the two large modules immediately before the first phase that lands substantial work in
   them, not at the end. See "Review outcome".

## Phases

### P0 — Absorption pipeline and regression gates

A consequence of the hard-fork decision; it must exist before the first upstream update is
considered.

- A repeatable upstream review process: detect, classify as absorb/reject/hold, record, advance
  `upstreamBase`. The existing evidence and ledger machinery is the intended home. Security-
  sensitive upstream paths are named watch targets.
- A translation ledger mapping upstream files and functions to fork equivalents.
- A committed performance benchmark reproducing the measured evidence, with thresholds.
- Protocol drift detection against the pinned `0.145.0`/`0.146.0` contract snapshots.
- `V1` and `V2`: make the wired validator honest and give the five orphaned suites a trigger.

**The v0.2 continuity gate, and how this program is admitted to it.** Not in the original catalog,
found while asking what would actually gate this branch. `.github/workflows/portability-ci.yml`
runs on `pull_request` — it is `pull-request-ci.yml` that is dispatch-only — and every one of its
four platform legs runs `scripts/validate-p5.mjs`, with the Windows leg running `npm test`. That
validator and `scripts/validate-portability.mjs` enforce a freeze anchored to
`099afca5946debe5620411f2ab1d4aec388918ca`: a path allowlist of what a descendant may change, a
byte-for-byte match for everything else, per-file digests for the inherited tests, and an exact
reviewed transformation for two of them.

Measured: at `4d2a7d6`, before any code landed, `validate-p5` and `validate-portability` both
exited 0. From `3a1c8c2` onward they did not, and nobody noticed for nine commits, because
`npm test` does not run the validators and nothing else did either. The claim "the failing set is
identical" that each phase reported was true of the suite that ran, and that suite did not contain
this gate.

Resolved by admission, not by re-baselining. `PORTABILITY_BASE` stays where it is, because moving
it would assert that ten unreviewed commits are the new reviewed base — the exact claim the gate
exists to stop anyone making by accident. Instead the seven v0.3 paths are listed one at a time in
the allowlist, so the diff that admits them is the review; the two inherited tests move from v0.2's
exact-transformation spec to the registry digest that `p5-validation.mjs` already enforces, because
that spec described one reviewed change and v0.3 makes many; and the continuation learns two more
consumable errors — an added test the frozen inventory count cannot hold, and a touched skills path
— each conditioned on the portability gate having already admitted the path.

Advancing `PORTABILITY_BASE` to the reviewed v0.3 head is the **closing** commit of this program,
after CI is green and the work is reviewed. That is the same order v0.2 used when it wrapped P5.

Proven still enforcing, by probe: a frozen file changing, an inherited test changing without its
digest, and an unlisted new test appearing are each still rejected.

**`V1` is blocked until that closing re-baseline, and every route was tried.** The P3 baseline
asserts three things about the repository — the `pull-request-ci.yml` trigger, `package.json` at
`0.1.0`, and the plugin at `0.1.0` — and all three are false because v0.2 released. Making the
validator pass would mean declaring the repository is still v0.1. Changing the validator is out of
scope: `scripts/validate-p3.mjs` and `scripts/lib/p3-validation.mjs` are outside the portability
allowlist, and admitting them to it would rewrite, unreviewed, the validator whose recorded
evidence is the P3 baseline — the same claim that keeps `PORTABILITY_BASE` where it is. Restoring
the trigger is forbidden by `validateLegacyWorkflowArchive`, which requires the archive to be
present. And unwiring the npm script, which is what this finding proposed, is blocked from two
directions: `validate-p4.mjs:600` requires the `validate:p3` key to exist with that exact value,
and `tests/p3-security-baseline.test.mjs:220` asserts the same, and neither file may be changed.

What was done instead is the half of `V1` that is available and true: the two validators that do
pass, `validate-p5` and `validate-portability`, now have npm scripts. Before this the repository
advertised one check that cannot pass and none of the checks that gate it. `validate:p4` stays: it
aborts on a missing `plugins/codex/.generated`, which `npm run build` produces, so it is a build
prerequisite rather than a permanent failure — untested here, because that needs an install.

One consequence for `V2`, worth recording before someone walks into it: `validateLegacyWorkflowArchive`
requires `pull-request-ci.yml` to equal the released file with its `pull_request` trigger replaced
by `workflow_dispatch` — nothing else may differ, and restoring the trigger fails the check as
surely as editing a job would. So `V2` cannot be satisfied by touching that workflow at all. The
route is `portability-ci.yml`, which the allowlist admits, and which already runs `npm test` on the
Windows leg; the suites still without a trigger have to join it or a new workflow, not the archived
one. The registry now maps `tests/args.test.mjs` to the `unit` scenario, which is the mapping the
archived workflow cannot implement and the replacement will have to.

**`V2` was misclassified, and measuring it turned up something larger.** The finding reads "five
suites have no automatic trigger". Run the five and four of them fail — they are orphaned because
they cannot pass, not because nobody wired them. None of it is a v0.3 regression: the failure set is

That step has to sit **below** the frozen Windows block. `P6-POLICY-002` proves the gate still guards

appearing above it silently retargets the proof at something unfrozen. The first placement did

### P1 — The cheap critical trio

Three small, independent, high-severity fixes in three different files. Highest value per line in
the program.

- `C6` with `C7`: wire turn-completion rejection to connection loss, and stop the broker when its
  app-server dies so the loss reaches the client at all. Two small edits in two files; retires the
  entire permanently-`running` class and the unkillable-worker case. `C7` is a P3 file, taken here
  because `C6` is inert without it on the default transport.
- `A1`, `A2`, `A3`: fix the argument parser. A 128-line file touched by no other phase. `A1` closes
  a sandbox escalation reachable from ordinary prose; `A2` makes native Windows paths work at all.
- `F1`, `F2`, plus memoization of the executable lookup and the workspace root: 49x on state reads
  and 139x on state updates, measured. `R2` lands here because it is the same file.

The memoization cache is per process, never shared or persisted. A cached answer can go stale if
the repository boundary or `PATH` changes within one process lifetime; short-lived companion
invocations cannot observe this, and the long-lived broker must either scope its cache to its own
fixed cwd or expose an explicit invalidation point. The chosen boundary is stated and tested in the
phase design.

**Landed.** The boundary chosen was: cache the workspace root per requested cwd with no
invalidation point, because the broker never calls it and serves one fixed cwd anyway; cache
executable lookups only when they resolved, because `/codex:setup` installs Codex and rechecks
availability inside one process while a binary that resolved does not move. Both are pinned by
tests. `F1` moved the record validators onto an already-resolved jobs directory, which is what made
a validator spawn git and, on POSIX, create directories once per record. `F2` names the discarded
read for what it is — the guard that refuses to rewrite state pointing outside the managed jobs
directory, which `tests/portability/posix-state.test.mjs` asserts and Windows had no coverage for
until now — and stops paying for it twice. `R2` became a compare-and-swap: each attempt commits
against the bytes it read and rebuilds on a competing writer rather than overwriting it, with the
last of three attempts committing unconditionally so the worst case is the old behaviour rather
than a new failure. It is not a lock; the check-to-rename window is two syscalls and the code says
so.

Measured on the same host as the baseline, medians (steady state, after the first resolution):

| | before | after | |
| --- | --- | --- | --- |
| `resolveCommandInvocation("git")` | 37.85 ms | 0.08 ms | 473x |
| `resolveStateDir()` | 70.23 ms | 0.05 ms | 1,405x |
| `loadState()` n=50 | 3,504.62 ms | 0.57 ms | 6,148x |
| `upsertJob()` n=50 | 10,555.18 ms | 1.87 ms | 5,644x |

The cold cost is unchanged and now explicit: the first workspace-root resolution in a process still
costs 73.5 ms, once. The suite shows the same shape end to end — `saveState prunes the index
without deleting dropped job artifacts` went from 19,465 ms to 106 ms.

### P2 — Hooks

`session-lifecycle-hook.mjs`, `stop-review-gate-hook.mjs`, `hooks/hooks.json`.

`C3` budget, `#528` dedup, `H1` buffer limit and status classification, `H2` timeout headroom and
grandchild termination, `S4` spawn-option consistency. Reachable only after P1.

**Landed.** Measured first: after P1 the `SessionEnd` hook costs 193 ms with nothing to clean up,
199 ms with five finished jobs, 323 ms with a running job whose process is gone, and 297 ms with a
live broker to shut down. None of that threatens a three-second clamp, so `C3` came down to the one
consumer that scales without bound — the POSIX confirmation poll, which waited up to three seconds
*per job*, so two unresolved jobs outlasted any budget the host allows. It now shares one deadline,
counted from process start rather than from the function, because the host's clock starts when it
spawns the hook. `#528` deduplicates by exact line: four `SessionStart` events wrote twelve export
lines and now write three. `H1` reads the review child through a capped stream instead of a default
buffer, so an overflow no longer arrives as a null exit status that reads as a failed review, and
every reason the gate emits is bounded — a child that fails with 50 KB of stderr now produces a
2,043-character reason instead of all of it. `H2` gives the review the hook's timeout minus a
reserve, so a timeout still has budget to emit the prepared decision, and terminates the child as a
process tree so the app-server it started does not outlive it. A test ties the mirrored timeout
constant to `hooks.json`, which is the drift that created `H2`. `S4` added the missing `windowsHide`
and deliberately did not unify `detached`; see the finding.

### P3 — Broker lifecycle

`broker-lifecycle.mjs`, `app-server-broker.mjs`.

`C4` idle timeout and orphan reclamation, `M5` backpressure, `S1` Windows validation and teardown
containment, `S3` false shutdown acknowledgement, `C1` and `C2` POSIX recovery, `R1` handler
serialization as hardening.

**Landed.** `S1` now validates Windows broker state the way POSIX state is validated, on read and
on write, and the teardown acts only on paths it derives from the recorded session directory —
which must sit directly under `os.tmpdir()`. A descriptor that does not validate gets no kill and
no unlink, and reading one returns null so the state self-heals. **The scope of that claim is
narrower than "Windows broker state is now trustworthy":** the Windows pipe has no handshake, so a
same-user attacker can still write a fully well-formed descriptor pointing at a pipe they own and
have the client talk to them. What the validation removes is arbitrary file deletion, a kill driven
by an arbitrary-shaped file, and the environment-variable fallback in the `SessionEnd` hook — whose
`CODEX_COMPANION_APP_SERVER_PID_FILE` and `..._LOG_FILE` have **no producer anywhere in the
repository**, only that one consumer. Authenticating the Windows pipe is the fix that would close
the rest, and it is not in this phase. `S3` reports a shutdown as stopped only when the broker
answered with a result. `C4` reclaims a broker that has had no client for thirty minutes, which is
the backstop for a `SessionEnd` that never ran; verified by shortening the constant and watching a
broker collect itself six seconds after its last client left, with the next command starting a
fresh one. `M5` drops a connection whose write buffer passes 8 MiB rather than growing it, which
`C6` made legible: a lost connection now fails the client's turn instead of hanging it. `R1`
serializes each connection's chunk handling. `C1` reclaims a POSIX identity whose recorded process
is gone, treats state that no longer resolves as reclaimable rather than fatal — the session
directory lives outside the home directory holding `broker.json`, so losing one while the other
survives is the ordinary case — and stops the diagnostics dying with it: `getSessionRuntimeStatus`
now reports an unusable runtime instead of throwing. `C2` bounds the replay set by eviction instead
of refusing every handshake past 4,096; eviction cannot open a replay, because the recorded pair
contains a server nonce the broker draws fresh per connection.

Both halves of `C1` are POSIX-only paths that the Windows development host cannot execute. They
rest on review and on the Windows paths staying green; the portability lanes are where they run.

### P4 — Protocol client

`app-server.mjs`, plus the client-side parts of `codex.mjs`.

`P1` request deadlines, `P2` import timeout, `P3` buffer cap and shape validation, `M1` and `M2`
bounds, `#499`/`#640` server-to-client requests, `#382` per-workspace `CODEX_HOME`.

**Landed: `P1`, `P2`, `P3`, `M1`, `M2`.** Every request now carries a deadline — 60 s by default,
because every call this client makes is control plane and a turn's work arrives as notifications,
with the one slow call passing its own budget. A silent app-server now fails a request in
1,509 ms against a 1,500 ms deadline instead of holding it for the life of the process. `P2` puts
one deadline over the whole import: the old timer bounded only the wait for the completion
notification and was armed behind an unbounded request, so a request that never answered left the
rejection with nothing awaiting it. `P3` caps the pre-identification notification buffer and, more
to the point, fails a turn whose start response carries no id — measured at 774 ms against a shape
that previously hung forever. `M1` keeps the tail of retained stderr rather than all of it; `M2`
caps the client's unterminated line, which the socket side already bounded.

**Not landed: `#499`/`#640`, `#382`. Both need a maintainer decision, not more implementation.**

`#499`/`#640` is already specified in `tests/contract/server-request-cases-v1.json`: ten stable
methods with per-method unattended outcomes (`decline`, `cancel`, `error`), `-32601` reserved for
unknown methods, and `observedProduct.behaviorStatus` recorded as `red` against
`app-server.mjs`. What blocks implementation is the same fixture's `requiredTerminalPolicy` —
`respond-once`, `latch-block`, `interrupt`, `wait-for-terminal-or-teardown`. Those four terms
appear **nowhere else in the repository**, so their semantics would have to be invented, and this
is the surface that decides whether Codex is granted or refused something. Landing it also means
rewriting `P4-SERVER-REQUEST-002`, which asserts today's red behaviour exactly, and flipping
`observedProduct`.

`#382` names an upstream issue and a location — the ambient environment inherited at the
app-server spawn — but not a behaviour. The plausible reading, isolating `CODEX_HOME` per
workspace, would separate the plugin from the `codex login` credentials that live in the default
home, so implementing it from the issue number alone risks breaking authentication to fix
something unstated. It needs the issue text or the maintainer's intent first.

### P4.5 — Structural split

`F4` and `F5`, with the translation ledger from P0. Placed here because P5 and P6 are the first
phases to land substantial work inside the two large modules, and doing the split first means each
of those fixes is written once, in its final home.

**Landed, and narrower than the phase as written.** Two things were checked before splitting
anything. First, the premise: of P5's nine items only four land in the two large modules — `L2` and
`P4` in `codex.mjs`, `J1` and `J2` in `codex-companion.mjs` — and all four are bounded fixes. The
substantial work in those modules is P6's, so the payoff is mostly against P6, not P5. Second, the
verification available: 44 of the integration tests cannot execute on the Windows development host
because the fake Codex is reached through a `.cmd` wrapper, and those are exactly the tests that
would catch a split regression. A 2,500-line restructure validated by a suite missing its most
relevant 44 tests is not a trade worth making.

So `F4` took the one extraction that is closed and has a single entry point: the turn-capture state
machine is now `lib/turn-capture.mjs`, 600 lines with `captureTurn` as its door, and `codex.mjs`
went from 1,291 lines to 739. That is where `L2` lands and where P6's turn work would. The move was
performed mechanically rather than by hand, and characterized before and after across nine command
shapes — task with and without reasoning, with a subagent, with the parent `turn/completed`
missing, review, adversarial review clean and not, and `--json` — with byte-identical output
including every progress line.

`codex-companion.mjs` was **not** split and stays at 1,257 lines. Its clusters share helpers in
both directions — extracting the background worker, where `J1` and `J2` land, pulls
`executeTaskRun` and `createTrackedProgress` with it — so a safe split means moving several
clusters at once. That is the change whose regressions the unrunnable 44 would catch. It should be
done when either the fake-Codex path runs on the development host or CI is the gate.

`F5` was narrowed on evidence. Of 28 platform branches in the runtime, 11 are already parameterized
behind an injectable `platform` option, and the rest decide genuinely different things: process
ownership, state layout, which environment variables may be trusted, how a child is terminated.
Expressing those "once" would build the same false equivalence that made `S4`'s recommendation
wrong. One capability *is* tested repeatedly and now has a name — `supportsWorkerControl`, for the
authenticated per-worker control socket POSIX has and Windows does not, used at six call sites and
by the module that provides it. The branches stay where they are; only the capability is named.

The translation ledger this phase was to carry belongs to P0, which has not run.

### P5 — Job reliability

`J1` worker pre-flight and credential-directory cleanup, `J2` cancel acknowledgement window, `J3`
and `J4` job resolution and reporting, `G1` and `G2` review-context bounds, `L1` and `L2` log and
turn-state bounds, `M4` artifact cleanup, `P4` transfer ledger ordering.

**Landed: all ten.**

`M4`, `J1`, `J2`. A job dropped from the index can never be looked up again — every lookup goes
through the index — so its files were a leak rather than a record, observed in production as one
workspace holding no indexed jobs and eight artifact files. They are removed as the job is pruned,
skipping any job that might still be written to. Orphans from prunes that already happened are
**not** swept: that needs a generation-bound sweep, which would race a worker that has written its
file but not yet indexed it. `J1` marks the job failed when the worker fails its pre-flight, and
discards the worker capability directory with its credential file — five distinct throws used to
happen before `runTrackedJob` owned the status, into output set to `ignore`, leaving the job
`queued` with no pid and no explanation for as long as the workspace lived. `J2` stops the cancel
client writing a pre-cancel snapshot over the worker's newer record: it re-reads before writing and
leaves a record that has already moved. The acknowledgement window went from two seconds to
fifteen, because the worker's handler polls for thread identity and can spawn an app-server to
interrupt the turn before it can answer.

`J3`, `J4`, `L1`, `G1`, `G2`, `L2`, `P4`.

`L2` and `P4`. The turn state stopped keeping what nothing read: every assistant message was
retained at full length twice, once on start and once on completion, and completed command
executions — the largest thing a turn produces — were accumulated and handed back in the result
where no caller has ever touched them. `mergeReasoningSections` is linear now instead of scanning
the accumulated list per element, which mattered because it runs once per reasoning item and its
result is persisted into the job payload each time. `P4` waits up to five seconds for the import
ledger rather than reading it the instant the completion notification lands: nothing enforces that
ordering, and that ledger holds the only handle to the imported thread, so a successful import
could report failure and lose it.

`G1` and `G2` — the `git.mjs` cluster. Untracked files now share the inline byte budget instead of
bypassing it: the guard measured tracked diff bytes only, and every untracked file was inlined at
up to 24 KB each regardless, so a few thousand of them built a prompt in the hundreds of megabytes
through a check that never saw them. `G2` puts an explicit 64 MiB ceiling on git output at the two
helpers every call goes through, rather than meeting `spawnSync`'s 1 MiB default as a raw
`ENOBUFS`; callers that deliberately measure against a smaller budget still override it.

`J3`, `J4`, `L1` — the `job-control.mjs` cluster. `matchJobReference` returns
null instead of throwing when nothing matches, which brings three downstream messages back to life;
asking for the result of a running job now says it is running rather than that a job visible in
status does not exist. Ambiguity still throws, because that is a distinct error with a distinct
fix. The recent list selects before it caps, so nine active jobs no longer empty a report that has
finished jobs behind them. The progress preview reads a bounded tail rather than the whole log,
which a status poll was re-reading every two seconds for up to four minutes against a file that
grows with every assistant message.

`tests/job-control.test.mjs` is new — the first coverage this module has had — and all three tests
were confirmed to fail against the source at the parent commit. Adding it meant admitting it in
four places: `package.json`, `CURRENT_TEST_COMMAND`, the portability allowlist, and the registry's
unit scenario. That is the routine the continuity gate now imposes on every new test file, and it
is cheap.

gpt-5.6 family, sharded parallel review, additional hook events, and any remaining upstream feature

## Review outcome

Revision 1 was reviewed by four independent verifiers and one cross-provider design review. What
changed:

**Upgraded.** `C1`'s trigger is far broader than a reboot clearing a temporary directory: any
broker death other than a clean authenticated shutdown arms it, and the plugin's own diagnostics
throw too. Verified locally that plugin data lives under the home directory while the POSIX session
directory does not, so the asymmetry the finding needs is the production default. Two of five real
workspaces already hold the precondition.

**Added.** `C6` — found by a reviewer, not by the original pass, and it is the highest-value fix in
the program. Also `A1`–`A3`, `G1`, `G2`, `J1`–`J4`, `H1`, `H2`, `L1`, `L2`, `P1`–`P4`, `M5`, `S3`,
`V1`, `V2`.

**Corrected downward.** `R1` is latent, not live. `M2`'s blast radius is a short-lived process, not
the broker. `C4` does not affect Windows at all and its POSIX case is narrower than stated. `C2`'s
"cannot be stopped" was too strong, and the claim that the worker-control module shares the defect
was wrong — its nonce set is per job. `S4`'s console-flash symptom is not established. The
dead-branch claim in `terminateProcessTree` was wrong: the path is unreachable dead code, not a
reachable one, so that finding is dropped. "644 lines never execute" was too strong on two counts.

**Corrected on severity.** The headline per-turn cost was quoted at the 50-record worst case. Real
usage is 0–1 records, roughly 345 ms per turn today. The honest claim is linear degradation toward
the worst case, and the amplifier is record shape rather than record count.

**Cross-provider review — applied in part.** The reviewer argued the structural split should come
first, on the grounds that landing six phases of fixes inside the two large modules and then
splitting them is more total work, and that the stated reason for deferring — keeping hand
translation of upstream changes cheap — does not survive a permanent stop to merging. **The second
point is accepted: that justification was weak and is withdrawn.** The conclusion is **declined as
stated**, because it rests on a premise introduced by the briefing rather than by the plan: P1
through P4 touch entirely different files, and only P5 and P6 land substantial work in the two
large modules. The split therefore moves from last to `P4.5`, immediately before the first phase
that needs it — neither where revision 1 put it nor where the reviewer proposed.

## Risks accepted by the hard-fork decision

1. Upstream security fixes no longer flow automatically. P0 names the watch targets.
2. Codex app-server protocol drift outranks any single defect here. The pinned snapshots are the
   right asset; nothing reports drift today. Covered in P0.

## Out of scope

- Contributing changes upstream.
- Publishing to npm or any central marketplace.
- Expanding support beyond the four declared tuples.
- Adding runtime dependencies for sockets, authentication, locking, or process control.
