# Post-v0.3 decisions: drift measured, two blockers unblocked

**Status:** Research complete, nothing implemented. This document exists to convert three open items
from "blocked on information" into "decidable", and to say plainly which of them are now decided by
evidence and which still are not.

**Reads before this one:** `docs/superpowers/plans/2026-08-15-post-v0.3-handoff.md` for what was
open, and `docs/superpowers/specs/2026-08-14-v0.3-hardening-program-design.md` for the program that
left them open. This file does not repeat either.

**What changed since the handoff:** the drift question is answered by measurement rather than by
recall; `#382` has its issue text and turns out to name its own fix; `#499`/`#640` have their issue
text and turn out to be a narrower problem than the catalog recorded, with one genuinely undecidable
piece left. No code was changed and no repository file outside `docs/superpowers/` was touched.

---

## 1. Protocol drift — measured, and it does not reach this plugin

The handoff put this first because everything else was downstream of it. It is answered.

### How it was measured

Three independent measurements, which agree.

**(a) From the installed binary.** `codex app-server` exposes `generate-ts` and
`generate-json-schema`, each with an `--experimental` flag — the same four surfaces the committed
snapshot tree holds. All four were generated from the installed `0.147.0` into a scratch directory
outside the repository, with the environment scrubbed to `SYSTEMROOT`/`WINDIR`/`TEMP`/`TMP` exactly
as `scripts/generate-p4-contracts.mjs:47-52` does, so that the `[features]` section of a local
`config.toml` could not skew the output. The result was diffed against the committed `0.146.0` tree.

**(b) Through the repository's own extractor.** `readMethodInventory` from
`scripts/lib/p4-snapshot.mjs:86-98` was imported read-only and run over the freshly generated
JSON-Schema surfaces, then compared against the `methods` arrays the committed
`snapshot-manifest.json` already carries. This is the apples-to-apples comparison: the repository's
own extraction convention on both sides.

**(c) From upstream public source.** `codex-rs/app-server-protocol` was fetched at tags
`rust-v0.146.0` and `rust-v0.147.0` and diffed — the macro definition blocks in
`protocol/common.rs` plus the checked-in schema artifacts.

**Why the committed generator itself was not used.** It refuses, for three reasons that are all
correct behaviour on its part. `assertSnapshotHost` (`scripts/lib/p4-snapshot.mjs:32-38`) compares
`process.versions.node` against the string literal `"24.18.1"`; this host runs `24.19.0`, so it
throws before argv is even parsed. `verifyExecutable` (`scripts/generate-p4-contracts.mjs:96-98`)
digest-checks against the two already-pinned binaries, so a `0.147.0` executable fails on
`P4E_CODEX_DIGEST` before its `--version` is read. And both `--codex-current` and
`--codex-previous` are mandatory (`:32-36`) with the lane loop hard-coded to
`["current", "previous"]` (`:142`) — there is no single-lane mode. The generator is a thin wrapper
over four command lines; running those four into a scratch directory reproduces the surface at zero
blast radius, which is the route taken.

### What moved

Measured by the repository's own extractor, pinned `0.146.0` manifest against installed `0.147.0`:

| Surface | 0.146.0 | 0.147.0 | added | removed |
| --- | --- | --- | --- | --- |
| stable `clientRequests` | 90 | 95 | 5 | **0** |
| stable `serverRequests` | 10 | 10 | 0 | **0** |
| stable `serverNotifications` | 70 | 70 | 0 | **0** |
| experimental `clientRequests` | 127 | 133 | 6 | **0** |
| experimental `serverRequests` | 11 | 11 | 0 | **0** |
| experimental `serverNotifications` | 70 | 70 | 0 | **0** |

The five stable additions are `thread/section/move`, `threadSection/create`, `threadSection/delete`,
`threadSection/list`, `threadSection/update`; the sixth experimental one is `plugin/search`. The
naming inconsistency between `thread/section/move` and the four `threadSection/` siblings is real and
present in the upstream source, not an artifact of extraction.

At file level: `stable/typescript` gained 20 files, removed none, and changed 21 of 622.
`experimental/typescript` gained 22, removed none, changed 24 of 701.

Four shape changes in the stable TypeScript surface are breaking in the strict sense:

- `v2/Thread.ts` — `isPinned: boolean` **removed**, replaced by `section: ThreadSection | null` and
  `sectionEnteredAt: number | null`.
- `v2/ThreadListParams.ts` — `isPinned?: boolean | null` **removed**, replaced by
  `sectionId?: string | null`.
- `v2/CommandAction.ts` — the `read` variant's `path` moved from `AbsolutePathBuf` to
  `LegacyAppPathString`. Both are strings on the wire; the constraint "guaranteed to be absolute and
  normalized" is gone. This is a **loosening** of validation, on the type that carries a path into a
  command-execution approval.
- `v2/ToolRequestUserInputParams.ts` — gains a **required** `isBlocking: boolean`, and
  `autoResolutionMs` picks up the only `@deprecated` marker in the whole bundle: "Use `isBlocking` to
  decide whether the request should block."

The rest is additive: `InitializeCapabilities` gains `extensions?`, `ImageGenerationItem` gains
`transparentBackground?`, `v2/Model` gains `modelSpecialty`, `v2/ThreadItem` gains `readOnlyHint`.
Three enums widen (`PlanType`, `McpAuthStatus` gains `"unknown"`, `ThreadSortKey` gains
`"section_position"`). One doc-only change is worth noting because it is a semantic statement about
the declared primary platform: `PathUri` now reads "Windows path equality and hashing ignore ASCII
case, while POSIX paths remain case-sensitive."

`0.147.0` is not the immediate successor of `0.146.0`. `0.146.1` sits between them, released
2026-08-05, and its entire release body is one non-protocol fix. Neither release note mentions the
app-server, JSON-RPC, or the protocol schemas at all — the five new methods appear only as
"Organize conversations into persistent, manually ordered sections."

### What it means here: nothing

The plugin spawns `codex app-server` with no `--experimental` flag
(`plugins/codex/scripts/lib/app-server.mjs:254`) and declares `experimentalApi: false` (`:51`), so it
faces the stable surface.

It names 23 wire methods, in three roles:

- **Sent (13)** — `initialize`, `initialized`, `thread/start`, `thread/resume`, `thread/list`,
  `thread/name/set`, `thread/compact/start`, `turn/start`, `turn/interrupt`, `review/start`,
  `account/read`, `config/read`, `externalAgentConfig/import`.
- **Handled as inbound notifications (6)** — `thread/started`, `thread/name/updated`, `turn/started`,
  `turn/completed`, `item/started`, `item/completed`. These are the complete set `turn-capture.mjs`
  switches on.
- **Declared unwanted (4)** — `item/agentMessage/delta`, `item/reasoning/textDelta`,
  `item/reasoning/summaryTextDelta`, `item/reasoning/summaryPartAdded`. These appear only in
  `DEFAULT_CAPABILITIES.optOutNotificationMethods` (`app-server.mjs:53-58`); there is no handler for
  any of them. They matter to drift for a reason the other two roles do not: opting out names a
  method by string, so a renamed or removed notification would make the opt-out silently stop
  working and the traffic would return.

**All 23 are present in the `0.147.0` stable surface; none is missing, renamed, or moved.**

The set is complete rather than sampled: every method this client originates is a string literal at
its call site — verified across every `request`/`notify`/`sendMessage` call under
`plugins/codex/scripts` — and none is composed at runtime. The two apparent exceptions,
`appClient.request(message.method, …)` at `app-server-broker.mjs:358` and `:373`, are pass-throughs
that forward whatever a connected client sent, and those clients are this same code. The plugin's own
`broker/hello`, `broker/auth` and `broker/shutdown` are its private broker protocol, not app-server
methods, and are correctly outside this set.

Against the changed and removed field names, the runtime under `plugins/codex/scripts` yields:
`isPinned` 0, `sectionId` 0, `autoResolutionMs` 0, `isBlocking` 0, `transparentBackground` 0,
`modelSpecialty` 0, `readOnlyHint` 0, `mcpServerOpenaiFormElicitation` 0, `PlanType` 0,
`McpAuthStatus` 0, `ThreadSortKey` 0. Two names do appear — `optOutNotificationMethods` and
`requestAttestation`, once each — and both are `InitializeCapabilities` fields whose only change in
`0.147.0` was a sibling field being added beside them.

### One surface nobody had noticed is unpinned: the type layer

The runtime is one thing; the build is another, and the build is where drift actually reaches this
repository first.

`plugins/codex/scripts/lib/app-server-protocol.d.ts` imports its types from
`../../.generated/app-server-types/index.js`. That tree is produced by `npm run prebuild` →
`scripts/generate-app-server-types.mjs`, which resolves whatever `codex` is on `PATH` and generates
against it. **It carries no version pin** — searching that script for a version literal, a pin, or an
expected-version check returns nothing, unlike `generate-p4-contracts.mjs`, which digest-checks and
version-checks before generating anything. And `plugins/codex/.generated/` is gitignored
(`.gitignore:150`) and holds zero tracked files, so there is no committed artifact to compare
against either. On this host the type layer would now be generated from `0.147.0`.

Four of the types that changed are imported by that `.d.ts`: `InitializeCapabilities`, `Thread`,
`ThreadItem`, `ThreadListParams`. That is the exposure. It resolves clean, determined statically:

- `InitializeCapabilities` is used as the type of a `DEFAULT_CAPABILITIES` object literal declaring
  `experimentalApi`, `requestAttestation` and `optOutNotificationMethods`
  (`plugins/codex/scripts/lib/app-server.mjs:50-52`). All three still exist; `extensions` is
  optional.
- `ThreadListParams` is used at the one `thread/list` call, which passes
  `{cwd, limit, sortKey: "updated_at", sourceKinds, searchTerm}` (`codex.mjs:713-719`). `cwd`,
  `sourceKinds` and `searchTerm` all still exist in the `0.147.0` type; `"updated_at"` is still a
  `ThreadSortKey` variant, which only widened. The removed `isPinned` is not passed.
- `Thread` and `ThreadItem` are re-exported, not constructed, and the only field read off a thread is
  `name`, which is unchanged. `ThreadItem`'s change was purely additive.
- The runtime references `isPinned`, `sectionId` and `autoResolutionMs` zero times, in the `.d.ts`
  and in the scripts alike.

**Since confirmed empirically.** `npm ci` (three packages, zero vulnerabilities, lockfile unchanged)
followed by `npm run build`: `prebuild` generated 642 type files from the installed `0.147.0`, and
`tsc -p tsconfig.app-server.json` exited 0. **The type layer compiles against `0.147.0` with no
errors.** The static determination above holds.

The finding that outlives this particular version, though, is the asymmetry: **the contract snapshots
are pinned to the byte and the type layer is pinned to nothing.** A newer Codex on a developer's
`PATH` silently changes what the build compiles against, with no gate and no record. That is a
smaller P0 item than the drift detector but the same kind of thing, and it is cheaper.

### So: the protocol moved, and it did not move under this plugin

P6 is unblocked. The handoff's framing — "work on features is speculative until this is answered" —
was right to demand the measurement, and the measurement clears it.

### DECIDED — do not re-snapshot now

Two reasons, and the second is the load-bearing one.

The drift does not reach the plugin, so a fresh snapshot buys no correctness today. And a committed
`0.147.0` tree is not a patch, it is a re-baseline.

**Measured, not inferred.** A single file placed at `contracts/codex/snapshots/0.147.0/probe.json`
and then removed produced, on this host at `4f26099`:

```
validate-portability.mjs  exit 1   P6E_SCOPE:contracts/codex/snapshots/0.147.0/probe.json
validate-p5.mjs           exit 1   P5E_IMMUTABLE_PATH:contracts/codex
                                   P5E_IMMUTABLE_PATH:package-lock.json
                                   P5E_IMMUTABLE_PATH:plugins/codex/agents
                                   P5E_IMMUTABLE_PATH:plugins/codex/scripts
                                   P5E_IMMUTABLE_PATH:plugins/codex/skills
```

The last four are the cascade worth noting: they are paths the continuation filter normally consumes,
and one out-of-scope file disables that filter by making the portability gate dirty, so complaints
that have nothing to do with the change surface alongside it. A real tree is roughly 1,900 files, each
raising its own `P6E_SCOPE`. Beyond the gates it would require editing
`contract-tools-v1.json` (new artifact, new lane), `snapshot-manifest.json` (new version, new
combined digest), the P4 evidence manifest, `validate-p4.mjs:264-269`'s two-element version literal,
four literals in `tests/p4-contract-baseline.test.mjs` including the pinned tree digest at `:355`,
and `scripts/lib/p5-validation.mjs:3408-3411`'s `p4SnapshotSha256` — several of which sit inside the
immutable set they would have to be edited to satisfy. That circularity is what the freeze exists to
create, and it should be paid deliberately at a re-baseline, not incidentally to answering a
question.

One assertion is worth recording as already satisfied: `P4-SNAPSHOT-002`
(`tests/p4-contract-baseline.test.mjs:387-390`) requires stable 10 server requests / 70 server
notifications and experimental 11 / 70 **for every version in the manifest**. `0.147.0` meets those
counts exactly. When a re-baseline does happen, that check is not what will break.

### DECIDED — what the detector should key on, and why it is not file digests

The handoff's P0 names "protocol drift detection against the pinned contract snapshots" without
saying what it compares. The measurement answers that.

Of the 234 stable JSON-Schema files that changed between the two versions, **228 have a
byte-identical TypeScript counterpart**. Only 6 correspond to a real type change. A detector keyed on
JSON-Schema file digests would therefore report roughly 97 percent false positives, which is the same
as reporting nothing. The `snapshot-manifest.json` already anticipates part of this — its
`normalization` block records that "the upstream aggregate bundle uses nondeterministic map
iteration while its per-definition files remain byte-identical" — but the churn measured here is
broader than the one aggregate file that note covers.

The high-signal comparison is the method-set extraction the repository already owns:
`readMethodInventory` reads three files per surface and returns three sorted arrays. Comparing those
arrays against the manifest's own `methods` arrays is four files instead of 275, needs no
normalization, and moved 5/0/0 on exactly the change that mattered. **A detector should compare
method sets, and should treat file digests as a separate, lower-priority signal if at all.**

A second constraint shapes this and should be recorded before anyone designs around it: **the
protocol carries no version of its own.** `protocolVersion` occurs zero times in the entire
`0.147.0` aggregate bundle; `InitializeParams` carries only `clientInfo` and `capabilities`, and
`ClientInfo.version` is the client's version, not the protocol's. `InitializeResponse` requires
`codexHome`, `platformFamily`, `platformOs`, `userAgent` — no protocol identifier. Negotiation is
capability-based, and `0.147.0` is where that mechanism grew: `InitializeCapabilities.extensions` is
new, and `mcpServerOpenaiFormElicitation` is simultaneously re-documented as "Legacy opt-in for the
`openai/form` MCP extension. New clients should declare `openai/form` in [`Self::extensions`]."
There is no deprecation policy document; deprecation is expressed ad hoc in doc comments. **A
detector cannot ask the protocol what version it speaks. It has to diff the surface.**

### A dated fact the handoff did not have

`contracts/codex/contract-tools-v1.json` carries a review policy with `reviewedAt: 2026-07-31` and
**`expiresAt: 2026-08-31`** — sixteen days from this document. Its `driftTriggers` list begins with
`new-stable-codex-release`, and its `rejectedOrDeferred` block defers candidate `0.147.0-alpha.2`
with the reason "official prerelease/alpha, not a stable blocking lane".

`0.147.0` stable was released 2026-08-07. **The stated reason for deferring it has expired**, and the
first declared drift trigger has fired. Nothing evaluates either: `driftTriggers` is validated only
for non-emptiness (`scripts/lib/p3-validation.mjs:348-351`), and no code anywhere in the repository
compares an installed Codex version against the pinned ones — every `--version` read asserts a
match against an already-pinned literal and fails otherwise. The one place the product reads the
installed Codex, `getCodexAvailability` (`plugins/codex/scripts/lib/codex.mjs:395-413`), returns the
version string as an opaque `detail` and never parses it.

**The tools-manifest review is due before 2026-08-31 regardless of what is decided about
re-snapshotting.** That is a calendar item, not an engineering one, and it is the natural moment to
fold in the `0.147.0` lane decision.

## 2. `#499`/`#640` — narrower than the catalog recorded, and one piece is genuinely undecidable

### What the issues actually say

Both are in `openai/codex-plugin-cc`. `#499` (opened 2026-07-14, zero comments) is titled
"Connector (codex_apps) MCP tool calls are auto-rejected: app-server client stubs all
server→client requests with -32601". `#640` (opened 2026-08-13, one comment, from its own reporter
and off-topic) is "Plugin never answers MCP tool-call approval requests, so every MCP call in a
`task` run is denied". Both quote the `handleServerRequest` stub verbatim.

**Both are exclusively about the MCP elicitation channel.** Neither issue, and neither of the two
open pull requests attached to them (`#501`, `#641`), addresses `execCommandApproval` or
`applyPatchApproval`. `#640` goes out of its way to say MCP travels a separate channel from
exec/patch approvals. Both proposed patches keep `-32601` for every other server-to-client method.

This corrects the finding catalog, which recorded `#499`/`#640` as "MCP and approval requests are
always denied" and treated them as one surface. They are one *mechanism* — the blanket stub — and
the reported half is MCP only. **What a headless client should answer when asked to approve a command
execution or a file change is not addressed by these issues at all.**

### The mechanism, verified against the installed binary

MCP tool calls are gated behind `mcpServer/elicitation/request`, not the exec/patch approval
channel. This is why `approvalPolicy: "never"` — which
`buildThreadParams`/`buildResumeParams` already set on every thread — does not unblock them, and two
reporters independently verified that setting `approval_policy = "never"` in the user's own config
changes nothing either.

Upstream has already modelled the distinction. The current config reference documents
`approval_policy = { granular = { sandbox_approval, rules, mcp_elicitations, request_permissions,
skill_approval } }`, and the `mcp_elicitations` key reads: "When `true`, MCP elicitation prompts are
allowed to surface instead of being auto-rejected." All five of those key names, plus
`codex_approval_kind`, `mcp_tool_call`, `tool_suggestion`, and `default_tools_approval_mode`, are
present as strings in the installed `0.147.0` binary. **There is an upstream vocabulary for this
decision, and it should be adopted rather than invented.**

The elicitation params type, generated from the installed binary, is a three-way union — and this is
the whole security shape of the problem:

```
McpServerElicitationRequestParams =
  { threadId: string, turnId: string | null, serverName: string } & (
    { mode: "form",        _meta: JsonValue | null, message, requestedSchema: McpElicitationSchema } |
    { mode: "openai/form", _meta: JsonValue | null, message, requestedSchema: JsonValue } |
    { mode: "url",         _meta: JsonValue | null, message, url: string, elicitationId: string } )
```

One method carries privileged tool-approval prompts *and* ordinary form, OpenAI-form, and URL
elicitations. Answering `accept` to the method is answering `accept` to all four.

### What the code actually looks like, and two stale citations

The stub is `plugins/codex/scripts/lib/app-server.mjs:220-225`, not `:163-168` as the v0.3 catalog
records; the app-server spawn is `:253-266`, not `:201-209`. Both citations drifted when P1–P3 and
`M1`/`M2` inserted code above them. Anyone working from the catalog's line numbers should re-derive
them.

`handleServerRequest` is defined once on `AppServerClientBase` and overridden by neither subclass, so
both transports share it. `setNotificationHandler` exists as a public seam for notifications; there
is no equivalent for requests.

**No path to a human exists in any context, and this is structural rather than incidental.** The
foreground command's stdout is captured as text; the background worker runs `detached` with stdio
`["pipe","ignore","ignore"]`; the broker runs `detached` writing to a log file; the Stop hook's child
gets no stdin at all. `AskUserQuestion` appears only in slash-command frontmatter — it is a tool the
model invokes *around* the node process, not a channel the process can reach. And under the broker
transport the app-server is owned by the broker's own client, which forwards notifications outward
and responses to client-initiated requests, but has no reverse frame class at all. Routing a
server-originated request to a client would be new protocol, not a new handler.

### The four `requiredTerminalPolicy` terms: they have no source

This was the stated blocker, and it is now answered — negatively, which is itself the answer.

Two exhaustive searches were run independently. Repository-wide, over every file type including
generated and vendored trees: `respond-once`, `latch-block` and `wait-for-terminal-or-teardown`
appear **only** in `tests/contract/server-request-cases-v1.json` and in the one paragraph of the v0.3
design document that quotes that fixture verbatim. No camelCase, snake_case, or prose variant exists
anywhere. Outside the repository: the GitHub issue and pull-request search scoped to the upstream
plugin repository returns zero for all three; they are absent from the upstream app-server README and
protocol source that was read, and an open-web search returns nothing. One apparent hit for
`latch-block` on upstream issue `#279` is a tokenizer false positive — that thread discusses a
"stop-after-first-failure latch" on a stderr progress reporter, an unrelated sense.

`interrupt` is the exception, and it is a different thing: `turn/interrupt` is fully implemented
(`plugins/codex/scripts/lib/codex.mjs:491-531`, with a broker special case that lets an interrupt
from another socket bypass the busy latch). That is client-to-server turn cancellation. Nothing
anywhere connects it to how a client answers an inbound request.

**These four terms are this repository's own vocabulary, and three of them have no definition
anywhere in or out of it.** The fixture that introduces them also records `"latch": false` and
`"interrupt": false` under `observedProduct`, and `contracts/codex/finalizer-characterization-v1.json`
describes the gap as "generic -32601 prevents automatic grant but does not latch, interrupt, or
confirm terminal failure" — both of which assert the machinery's *absence* without defining it.

The blocker was recorded as "their semantics would have to be invented". That is confirmed, and it
means the item cannot be closed by finding the answer. It can only be closed by someone deciding what
they meant, or by deleting them. **See §4.1 — this is the one piece that remains genuinely blocked.**

### DECIDED — the shape of the answer, and why the grant question dissolved

The decision framed as the maintainer's was whether Codex should be granted MCP capability from this
plugin. After §3 that question does not have a policy answer, because it does not have a technical
one: **the client cannot see what it would be granting.** A grant decision needs an action to be
about, and the elicitation params carry no tool name and no arguments. So the maintainer's remaining
call is narrower and more honest — accept that MCP tool calls stay unavailable through this plugin
until the protocol carries approval provenance, and decide only how loudly that failure is reported.

**Must not: answer `accept` to the `mcpServer/elicitation/request` method as a whole.** The method
carries `mode: "url"` and two form modes that a headless client can neither render nor validate;
accepting them returns consent the user never gave and, for `url`, consent to an authorization flow
they never saw. This was raised against the upstream pull request by an automated reviewer and the
contributor accepted it — **and the narrowed version they shipped is itself broken**, for the reason
§3 gives.

**A first draft of the recommendation proposed an `accept` path gated on `mode === "form"` plus an
approval-kind discriminator in `_meta`. The cross-provider review in §3 broke it, and it is
withdrawn.** What follows is the revised shape. §3 carries the attack and the reasoning; the summary
is that `_meta` is written by the party being authorized, so gating on it is self-approval.

**Recommended shape**, default-deny, adopting upstream's own category vocabulary rather than the
fixture's invented one:

1. Replace the blanket stub with a per-method table. Genuinely unknown methods keep `-32601`; known
   methods get a well-formed protocol answer.
2. **No method answers `accept`.** Not `mcpServer/elicitation/request` in any mode, not under any
   per-run switch. The client cannot see the effect and target it would be authorizing — the
   elicitation params carry `threadId`, `turnId`, `serverName`, `_meta`, `message` and either
   `requestedSchema` or `url`, and **no tool identity and no arguments at all** — so there is nothing
   for a decision to be about. Restoring an `accept` path needs an app-server-generated provenance
   envelope that the MCP server cannot forge, which does not exist in the protocol today, and it
   needs its own security review.
3. Answer "no human is reachable" as `cancel`, not `decline`. `decline` asserts that a decision was
   made and the answer was no; a server may reasonably record that as a user refusal, suppress
   retries, or treat the exchange as normally handled and continue. `cancel` is the honest statement.
   Reserve `decline` for the case where a trusted local policy specifically forbids that exact
   action, and where no `cancel` exists in the response type, emit a well-formed error meaning
   headless interaction is unavailable.
4. The five approval methods answer as in (3) — and **`sandbox: "read-only"` is not the
   justification**. An approval request arriving at all means the standing authorization does not
   cover the action, which is equally true in write-capable mode. The reason not to accept is that
   nobody is present to authorize, not that the sandbox would contain it.
5. **Fail the operation rather than continuing past a refused approval.** This is the half the first
   draft missed and it is the one that bites users: a run that declines invisibly, does less work, and
   reports success is an integrity failure the user cannot see. Auto-accepting to avoid it would
   trade an integrity failure for a security one; the answer is to end the turn in a clear failure
   state and forbid a success report. Where there is no guaranteed channel to tell a human at all —
   the detached worker — the honest position is not to start work that needs reverse approval.
6. Treat `_meta` and `requestedSchema` as an untrusted parsing boundary: check object-ness, bound
   frame size, nesting depth and schema complexity. **Do not write raw `message`, `_meta`,
   `requestedSchema`, `url` or form content into the broker log** — a hostile server can otherwise
   push chosen content into a durable local artifact.
7. Refuse the *configuration* that would enable auto-accept, rather than refusing to run when such a
   request arrives. Refusing to run hands any configured hostile server a trivial denial of service.
8. `item/tool/requestUserInput` cancels, and must now account for `0.147.0`'s required `isBlocking`.
9. Landing any of this rewrites `P4-SERVER-REQUEST-002`
   (`tests/p4-contract-baseline.test.mjs:648-665`), which asserts today's `-32601` pair byte-exactly,
   and flips `observedProduct.behaviorStatus` from `red` in the fixture, in
   `contracts/codex/finalizer-characterization-v1.json:90-98`, and in
   `docs/baselines/2026-07-31-p4-contract-baseline.md:108-111`.

One diagnostic item from `#640` is worth taking regardless of the grant decision and costs nothing:
the failure currently surfaces as `Tool <server>/<tool> failed.`, and the real reason —
`user rejected MCP tool call` — is visible only in raw rollout JSONL. Propagating it into the job log
turns a multi-step investigation into a one-line answer.

**No maintainer position exists upstream to defer to.** Every participant across both issues and both
pull requests has `author_association: NONE`; there are zero comments from anyone in the owning

## 3. Cross-provider adversarial review of the riskiest choice

One pass, on one choice: what a client with no reachable human may answer to a server-to-client
request. The reviewer was given the protocol facts verbatim — the three-way elicitation union, the
`_meta: JsonValue | null` typing, the granular approval vocabulary, the plugin's defaults — and asked
to attack the proposal rather than survey it. Output is advisory. What follows is what was applied,
and the one thing that was not.

### Applied: the discriminator is broken (verdict BROKEN)

The proposal gated `accept` on `_meta.codex_approval_kind === "mcp_tool_call"`. The reviewer's
objection is that `_meta` is composed by the MCP server — the party whose request is being authorized
— so the gate asks the applicant to certify its own application. The attack is concrete and needs
nothing exotic:

```
mode:            "form"
_meta:           { "codex_approval_kind": "mcp_tool_call" }
requestedSchema: { "type": "object", "properties": {}, "additionalProperties": false }
```

The empty-but-valid schema is the part that makes it clean: it sidesteps the objection that a headless
client could not produce form values anyway, because no values are required. A hostile or compromised
server obtains a protocol-level `accept` **issued by a trusted client**, and may treat it as human
consent or as the precondition for whatever it gated behind the elicitation.

The reviewer then closed the obvious patches. Checking `requestedSchema`'s shape fails because an
attacker can clone a legitimate schema. Allowlisting `serverName` fails because `serverName` is a
string the server itself supplies, not an authenticated identity. **What would work is provenance the
app-server generates and strips from server input — an approval envelope bound to the active thread
and turn, a canonical server identity, the tool name, normalized arguments, and a one-time call ID —
and that does not exist in the protocol today.**

This is confirmed independently by the type generated from the installed binary in §1:
`McpServerElicitationRequestParams` carries `threadId`, `turnId`, `serverName`, `_meta`, `message`,
and either `requestedSchema` or `url` + `elicitationId`. **There is no tool name and there are no
arguments anywhere in it.** So even with the forgery fixed, a client answering this request cannot
know which tool call it is approving.

One refinement the review did not make and the type documentation supports: `threadId` and `turnId`
*are* app-server-supplied rather than server-supplied — the type's own comment says `turnId` "is
nullable because MCP models elicitation as a standalone server-to-client request... turn context is
app-server correlation rather than part of the protocol identity of the elicitation itself." So they
are real, if partial, provenance. They identify the *conversation*, never the *action*. Requiring a
non-null `turnId` is worth doing and does not come close to sufficing.

**Applied in full.** The `accept` path is withdrawn from the recommendation, including the
opt-in-per-run form. This also means the first draft's framing was wrong in kind, not degree: the
question was treated as "under what policy may we grant this", when the protocol does not yet carry
enough information for granting to be a decision at all.

### Applied: `decline` is not a free rename of `-32601` (verdict WEAK)

`-32601` says "I do not implement this method." `decline` says "I implement it, I processed your
request, and the answer is no." The reviewer's point is that honest servers may act on the difference:
on `-32601` a server may disable the capability or take a non-interactive fallback; on `decline` it
may record a *user refusal*, suppress retries, or treat the exchange as normally handled and let the
loop continue. That produces a false consent history and a partial-success risk.

The reviewer was explicit that this is not an authorization bypass and that no concrete escalation
path is demonstrable from the facts given — it is recorded here as WEAK rather than BROKEN for that
reason.

**Applied** as items 3 and 5 of the revised shape: `cancel` for "no human is reachable", `decline`
reserved for a trusted policy that forbids the specific action, a well-formed "headless interaction
unavailable" error where the response type has no `cancel`, and — the substantive half — failing the
operation instead of continuing past the refusal.

### Applied, with one correction to the proposal's reasoning (verdict WEAK)

On always-declining the five approval methods the reviewer agreed with the conclusion and rejected the
justification. The proposal argued from `sandbox: "read-only"` being the default. The reviewer's
answer: even where a run has explicitly chosen write-capable mode, that is not blanket consent to
every command, patch, or permission escalation — **an approval request arriving is itself evidence
that the standing authorization does not cover the action**. The reason not to accept is the absent
human, not the sandbox.

The reviewer also named the failure mode the proposal had not: declining and continuing means the
agent does less work and reports success, invisibly, to a user who cannot see the refusals. It
explicitly refused the trade of accepting-to-avoid-that — "invisible incomplete execution is an
integrity failure and unauthorized execution is a security failure; do not permit the latter to avoid
the former."

**Applied** as items 4 and 5.

### Applied: omissions (verdict BROKEN)

Two that the proposal had not considered at all, both now in the revised shape:

- `_meta` and `requestedSchema` are an untrusted parsing boundary and were being treated as data to
  read a key out of. Object-ness, frame size, nesting depth and schema complexity all need bounds.
- **Raw elicitation content must not reach the broker log.** A hostile server otherwise has a
  primitive for writing chosen content into a durable local artifact, through a client that is
  trusted to write it. This one is worth its own note because the broker log is exactly where a
  headless client's diagnostics naturally go, and §2's own diagnostic recommendation — surface the
  real refusal reason instead of `Tool <server>/<tool> failed.` — points at the same file. **Surface
  the reason; do not surface the payload.**

### Declined: nothing

No part of the review was declined. Its one framing that needed adjusting rather than rejecting is
noted above: `threadId`/`turnId` are better provenance than the review's "the client sees nothing
trustworthy" implies, and still nowhere near sufficient.

### The consequence for upstream absorption

This is the part with the broadest reach, and it falls out of the review rather than being asked for.

Both open upstream pull requests attached to these issues ship an `accept` path.
`openai/codex-plugin-cc#501` answers `mcpServer/elicitation/request` with `action: "accept"`
unconditionally. `#641` was revised, after an automated reviewer raised the form/URL problem, to gate
on exactly `_meta.codex_approval_kind === "mcp_tool_call"` — **which is the construction the review
above breaks.** The bot's objection was real and the fix adopted for it is not sufficient: it closes
the "accepts every form and URL elicitation" hole and leaves the "any server can label its own
request" hole open.

Under the hard-fork decision, upstream changes are analyzed individually and absorbed or rejected.
**This is a concrete rejection with a stated reason**, and the first one this program has produced —
P0 has no ledger to record it in yet, which is itself an argument for building one. If either PR
merges upstream, absorbing it would import the flaw, and the fact that it merged upstream is not
evidence it is safe (nobody in the owning organization has commented on either).

## 4. `#382` — the issue names its own fix, and answers the objection to it

### What it actually says

`openai/codex-plugin-cc#382`, opened 2026-06-18, **zero comments in the fourteen months since**, no
label, no milestone, no linked pull request. Title: "Concurrent Claude Code sessions race on shared
`~/.codex` — app-server spawned without an isolated `CODEX_HOME`".

The handoff recorded this as naming "an issue and a location but not a behaviour", with
`CODEX_HOME` isolation as one plausible reading. That is not right: **isolation is the issue's own
explicit proposal, in a heading** — "Proposed fix — isolate `CODEX_HOME` per app-server, keyed by the
existing workspace identity", with the code line `env.CODEX_HOME = path.join(resolveStateDir(cwd),
"codex-home")`. That is the same `resolveStateDir` this repository already uses, so the path template
is one the plugin already computes.

The symptom, which is concrete and observable: N workspaces produce N concurrent app-servers all
writing one `~/.codex`, and that directory is not safe for concurrent writers. The evidence offered
is orphaned `..codex-global-state.json.tmp-<epoch>-<hex>` files — the fingerprint of atomic-rename
writers clobbering each other — alongside a runtime-mutated set spanning
`.codex-global-state.json`, four SQLite stores with their `-wal`/`-shm` companions,
`session_index.jsonl`, `models_cache.json`, `skills/`, and `shell_snapshots/`.

### The objection that blocked it is answered in the issue itself

The recorded reason for not implementing was that isolating `CODEX_HOME` would separate the plugin
from the `codex login` credentials in the default home. The issue anticipates exactly this and
proposes a seeding allowlist: symlink `auth.json` to the real one — "single source of truth; safe
across OAuth refresh-token rotation" — copy `config.toml` and `hooks.json` at `0600` because Codex
writes trust hashes and toggles back into them, symlink static user assets, and let everything else be
recreated inside the isolated home. The reporter claims to have verified it end to end:
`CODEX_HOME=<seeded home> codex login status` returning "Logged in using ChatGPT" while the SQLite
stores, session index and skills stayed isolated.

Upstream documentation confirms the risk is real but conditional. `CODEX_HOME` "sets the root for
Codex state, including config, auth, logs, sessions, skills, and standalone package metadata", and
credentials are cached "locally in a plaintext file at `~/.codex/auth.json` **or** in your
OS-specific credential store", selected by `cli_auth_credentials_store` (`file` | `keyring` | `auto`).
**On `keyring`, or on `auto` where an OS store exists, credentials are not under `CODEX_HOME` at all
and relocating it does not touch authentication.** Only the `file` case needs the symlink.

### A narrower mechanism exists, and it is not sufficient

This is the finding that changes the shape of the decision. Upstream offers `CODEX_SQLITE_HOME` (env)
and `sqlite_home` (config) — "Directory where Codex stores the SQLite-backed state DB used by agent
jobs and other resumable runtime state" — plus `log_dir`. All three are present as strings in the
installed `0.147.0` binary. They relocate the SQLite layer and the logs **without moving
`CODEX_HOME`, and therefore without touching `auth.json` at all.**

That covers four of the ten file groups the issue names. It does **not** cover
`.codex-global-state.json`, which is the headline evidence. No override was found for it, nor for
`session_index.jsonl`, `sessions/`, `models_cache.json`, `skills/`, or `shell_snapshots/`, in the
documentation or as an obvious knob. `CODEX_STATE_HOME` — which the issue itself describes as a
hypothetical upstream ask — is **absent from the installed binary**, confirming it does not exist.
Note also that `.codex-global-state.json` does not appear as a literal string in the binary either,
so its name is likely composed at runtime; that is an inference, and it means "absent from the
strings" is not proof there is no knob.

**So the trade is explicit:** `CODEX_SQLITE_HOME` + `log_dir` is a cheap, credential-safe partial
mitigation that leaves the reported symptom in place. Full `CODEX_HOME` isolation fixes the symptom
and costs a seeding allowlist plus the credential handling above.

### Two things any implementation must handle

**The plugin has its own reader that must move with the child.** `resolveCodexHome`
(`plugins/codex/scripts/lib/codex.mjs:142-144`) resolves `process.env.CODEX_HOME || ~/.codex` to find
the import ledger. Redirecting the spawned child's `CODEX_HOME` without redirecting this reader would
split the plugin's ledger view from the child's ledger writes — and `P4` exists precisely because
that ledger holds the only handle to an imported thread. The two must move together.

**There is an upstream pull request that collides.** `openai/codex-plugin-cc#369` ("per-workspace
broker ignores `CODEX_HOME` — make it account-aware so multi-account fallback works", open, unmerged,
+479/−11) treats a caller-set `CODEX_HOME` as *deliberate account selection*, because the broker
inherits it once at spawn time and `ensureBrokerSession` then reuses any live broker for that cwd
unconditionally. A plugin that unconditionally overwrites `CODEX_HOME` per workspace breaks that use
case outright. Neither issue mentions the other. Any design here has to answer: what happens when the
user has set `CODEX_HOME` on purpose?

### Environment handling, for context

Every one of the six spawns in the runtime passes the ambient environment through: the app-server
spawn (`env: this.options.env ?? process.env`, and in production no call site supplies `options.env`),
the broker spawn, the detached task worker (`env: process.env` literally), the Stop-hook child (a
spread of `process.env` plus one added key), and both process-resolution helpers. There is no
allowlist, no denylist, and no scrubbing anywhere under `plugins/`. The pattern of a *constructed*
environment does exist in this repository — `scripts/run-p4-lifecycle.mjs:364-377` builds a twelve-key
object including `CODEX_HOME`, and `scripts/generate-app-server-types.mjs:140-164` builds an
allowlist copy — just not in the product runtime.

For completeness: upstream's `shell_environment_policy` (`inherit`, `filters`,
`ignore_default_excludes`, `set`) governs what Codex passes *down* to shell commands it runs. It is
the opposite direction of travel and constrains nothing about what this plugin passes *in*. Its two
documentation pages contradict each other on whether `KEY`/`SECRET`/`TOKEN` variables are excluded by
default; that is worth knowing but does not bear on `#382`.

### DECIDED — decidable now, with one host fact outstanding

The decision is a maintainer policy call between two named options, and both are now fully specified:

- **Narrow:** set `CODEX_SQLITE_HOME` and `log_dir` per workspace. No credential risk under any
  store, no seeding, no collision with `#369`'s account-selection semantics. Leaves
  `.codex-global-state.json` contention — the reported symptom — unfixed.
- **Full:** `CODEX_HOME` per workspace at `path.join(resolveStateDir(cwd), "codex-home")` with the
  seeding allowlist, plus moving `resolveCodexHome` to match, plus an answer for a user-set
  `CODEX_HOME`. Fixes the symptom; costs the seeding surface and cross-project memory sharing, which
  the issue itself flags as the thing being given up.

The issue also flags "default-on vs an opt-in config flag, since per-workspace isolation stops
sharing codex's cross-project memory/history" as an open question of its own — that is a product
call, not a technical one.

**Outstanding host fact:** which credential store this machine uses decides how much the Full option
costs here. That probe was attempted and refused by the credential-path shell guard, which is correct
behaviour and was not worked around. It needs a `!`-prefixed run by the owner; see §5.

## 5. What is still information-blocked, and why

Each of these was looked for and not found. They are not pending work items — they are the specific
things that further research will not produce.

1. **The provenance of `respond-once`, `latch-block`, and `wait-for-terminal-or-teardown`.** Two
   exhaustive searches, one inside the repository over every file type and one across the upstream
   tracker, the upstream protocol source, and the open web, put these three strings nowhere except
   the fixture that introduces them and the design paragraph quoting it. They are not upstream

   `tests/contract/server-request-cases-v1.json` should be asked what they meant. If nobody can say,
   the honest close is to delete the `requiredTerminalPolicy` array and specify the surface in
   upstream's own terms (`mcp_elicitations`, `sandbox_approval`, `request_permissions`,
   `skill_approval`), which exist, are documented, and are present in the installed binary.

2. **Whether the app-server can supply forgeable-free approval provenance, now or planned.** This is
   the gap §3 opened, and it is the one that decides whether `#499`/`#640` is fixable here at all. The
   elicitation params carry no tool identity and no arguments, and the only unforgeable fields are
   `threadId` and `turnId`. Whether upstream intends an approval envelope — and whether
   `approval_policy.granular.mcp_elicitations` being *enabled* changes what the client receives, which
   nobody has tested — was not established. Reading `codex-rs` for how the TUI answers these requests,
   and what it validates before accepting, is the concrete next step and was not done here.

   Note what is **no longer** open: whether unattended command-execution and file-change approval
   should be granted. No issue covers it and no maintainer has stated a position, but §3 settles the
   engineering answer independently of policy — an approval request arriving is evidence the standing
   authorization does not cover the action, and there is nobody to extend it. The open half is not
   whether to refuse but what a refused run must then do, which §2 item 5 answers and no test covers.

3. **Which credential store this host uses.** Needed to price `#382`'s Full option here. The probe
   was refused by a mechanical guard and was not routed around.

4. **Whether the remaining `~/.codex` state can be relocated at all.** No override was found for
   `.codex-global-state.json`, `session_index.jsonl`, `sessions/`, `models_cache.json`, `skills/`, or
   `shell_snapshots/`, in the documentation or in the installed binary's strings. Absence from
   documentation is not proof of absence, and the file name may be runtime-composed. Settling it
   means reading upstream source for those specific paths.

5. **Whether concurrent app-servers against one `CODEX_HOME` are supported at all.** The upstream
   app-server documentation is silent — it documents methods and schemas, with no concurrency,
   locking, or state-ownership statement. `#382`'s central premise rests on the reporter's inference
   from orphaned temp files, which is suggestive but circumstantial, and on three open upstream issues
   that were cited but not read.

**Three items that were on this list have been removed, because they were measured and are not
blocked — see §6.** `P4-HANDSHAKE-001` passes. `P4-COMMAND-002` passes, so the "real drift,
uninvestigated" recorded against it does not exist. And the fake-Codex development-host limitation is
diagnosed: it is the host's 14,531-character `PATH` being dropped by `cmd.exe`, not a property of the
fixture, and it is fixed by shortening `PATH`.

### The two remaining failures, and what the owner decided about them

```

P5-POWERSHELL-001 P5E_NODE_IDENTITY_NODE_VERSION

`.github/workflows/portability-ci.yml:53` pins `node-version: 24.18.1`; this host runs `v24.19.0`.

**The owner's decision, recorded as an input rather than a proposal: this project runs a supported
*range* and the latest Node, not a pinned interpreter.** That reverses the recommendation this
document originally carried ("move the interpreter, not the pin"), and the rest of this section is
what that decision costs and what it does not.

**The repository already declares the range.** `nodeRange: ">=24.0.0"` exists in `toolchain.json`,
`contracts/codex/contract-tools-v1.json` and `ci/matrix-profiles-v1.json`, is frozen as a schema

#### The exact pin in `assertSnapshotHost` protects nothing measurable

Before relaxing anything, the question was whether the exact Node pin guards a real property.
`assertSnapshotHost` exists so snapshots stay byte-reproducible. Measured on Node `24.19.0` against a

inspectSnapshotTree over the committed tree   fileCount 3881      MATCH
                                              totalBytes 13852289 MATCH
                                              treeSha256 820456f8bdc229db…  MATCH
re-canonicalize all four v2 aggregate bundles 4 identical, 0 differ

The snapshot bytes come from a Rust binary; Node only runs it, sorts keys in one aggregate file, and
hashes. Both Node-touched steps reproduce exactly across versions. **Relaxing the version check is
therefore correcting an over-specified check, not weakening a real one.**

#### What was changed, and what refused to be changed

Probed rather than assumed. Appending a line to each candidate and running both gates:

| `tests/p5-matrix-profile.test.mjs` | admitted, no side requirement |

assertion against the declared range, which is the check that was missing. The gate's own logic stays

The registry digest was recomputed **canonically** (CRLF folded to LF, which is the form

Its failure is not a version string. `Get-P5ExecutionProvenance` is called with

produced the evidence. **Relaxing it would be weakening a check to make it pass, so it was not

host. CI runs it on the pinned runner and it passes there. On a machine that has deliberately chosen

statement, not a defect.

Measured after the change, across all five baseline suites: **77 tests, 76 pass, 1 fail**, that one

### A second, larger gap between this host and CI — diagnosed, and it is one line of environment

Run as CI runs it, the unit suite produces 46 failing assertions here, every one carrying the same
message: `Codex CLI is not installed or is missing required runtime support.` That is the fake-Codex
development-host limitation the v0.3 program recorded at 44 assertions and named as "exactly the
tests that would catch a split regression" — the reason `codex-companion.mjs` was not split. It was
recorded as a property of the fixture ("the fake Codex is reached through a `.cmd` wrapper"). **It is
not. It is the host's `PATH`.**

Measured, in order:

```
where.exe node                        -> C:\Program Files\nodejs\node.exe        (found)
cmd.exe /d /s /c "node --version"     -> 'node' is not recognized...             (not found)
cmd.exe /d /s /c "...\node.exe --ver" -> v24.19.0                                (node is fine)
PATH seen by the parent shell         -> 14,531 characters, 180 entries
PATH seen inside the spawned cmd.exe  -> EMPTY  (`echo %PATH%` prints "ECHO is on.")
same, with PATH shortened to 54 chars -> v24.19.0                                (resolves)
```

`SystemRoot`, `PATHEXT` and `NUMBER_OF_PROCESSORS` all survive the hop; `PATH` alone is dropped,
because 14,531 characters exceeds what `cmd.exe` will carry. The chain is then mechanical:
`resolveCommandInvocation` resolves `codex` to the fixture's `codex.cmd` correctly, via `where.exe`,
which sees the full `PATH`; it must then invoke a `.cmd` through `cmd.exe`; inside that `cmd.exe`
there is no `PATH`; the wrapper's `node "%~dp0codex" %*` cannot find `node`; the product reports
Codex as not installed.

**The same cause explains a second symptom nobody connected to it.** `npm run validate:portability`
and `npm test` fail here with the identical `'node' is not recognized`, because npm runs scripts
through `cmd.exe` on Windows. Every validator in this document had to be invoked as
`node scripts/validate-*.mjs` directly for that reason. And it explains why CI is green: a fresh
runner has a short `PATH`.

**This is a host defect, not a repository defect, and the fix is to shorten `PATH`.**

Audited, so the fix is surgical rather than a guess:

| scope | entries | chars | nonexistent |
| --- | --- | --- | --- |
| Machine | 14 | 421 | 0 |
| **User** | **176** | **15,348** | **167** |

166 of the 176 user entries match `…\Temp\TestRunCS<random>\001\run-<random>\dotnet\.dotnet\tools` —
a .NET test runner has been appending one entry per run to the **persisted** user `PATH`. Exactly one
other entry is nonexistent (`C:\Users\js\.dotnet\tools`), and it is a legitimate path that simply has
not been created; it should stay.

Removing only the leaked entries takes the user `PATH` from 176 entries / 15,348 characters to
**10 entries / 329 characters**, and the whole `PATH` from 14,531 to 751. Nothing legitimate is
touched.

The cleanup was run by the owner — it is a persisted user-environment change and was not made from
here. Measured afterwards:

npm test                           'node' is not recognized  ->  runs

```

### It is also a real product defect, found incidentally

`resolveCommandInvocation` routes **every** resolved `.cmd` or `.bat` through `cmd.exe`
(`process.mjs:54-77`). On Windows, `npm install -g` produces exactly such a shim, and the npm shim's
job is to invoke `node`. `/codex:setup` instructs users to run `npm install -g @openai/codex`.

So: **any Windows user whose `PATH` is long enough to be dropped by `cmd.exe`, who installed Codex
the way this plugin tells them to, gets "Codex CLI is not installed" from a working installation** —
with no diagnostic pointing at `PATH`, because `getCodexAvailability` computes a `detail` string
carrying the real `cmd.exe` error and every caller discards it in favour of the generic message.

This host is only unaffected in production because it also carries a native `codex.exe`, which
resolves to an `.exe` and never enters `cmd.exe` at all. That is luck, not design.

Two cheap mitigations, neither implemented here: surface `detail` when availability fails, and — when
invoking a `.cmd` — pass a `PATH` short enough to survive, or resolve the interpreter to an absolute
path rather than relying on the child's lookup.

### Why this is the finding that matters most

**The repository is green. The development host cannot reproduce it, for two independent reasons.**
Locally, 46 assertions read as failing that pass in CI, and 2 fail that CI never sees. Anyone
measuring here without knowing that will conclude the repository is broken in ways it is not — which
is exactly what happened, twice, in the record this document is correcting.

This is the same failure mode the v0.3 program closes with: *"Four separate measurements in this
session were wrong because the probe was handed different inputs than the code under test uses."* The
inputs differ by an interpreter version and a fixture resolution path, and both are fixable. Until
they are, every local measurement in this repository carries an asterisk, and the cost is not
hypothetical — it has now produced two rounds of phantom work items.

Nothing here was fixed. The measurement was run, the record is corrected, and the fix is item 1 of
the order below.
